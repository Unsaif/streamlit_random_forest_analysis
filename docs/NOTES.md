## Interpretations made in Phase 1 (conservative choices; flag if wrong)

1. **Fallback when no quantile satisfies the bound.** The plan says keep all positive-importance
   features and set `bound_satisfied = False`. The implementation keeps all of them *and
   re-evaluates the bound on that model*, reporting the actual outcome in `bound_satisfied`
   (`q_final` is `None` in this case). A flag that is always False would hide the case where
   the all-positive model does satisfy the bound.
2. **`index` split.** The remaining rows are split 75/25 train/validation *stratified*,
   matching the default method; if stratification is impossible (a class with one row) it
   falls back to a random split and emits a warning.
3. **Dtypes.** The preprocessor does not up-cast numeric columns to float64 when nothing needs
   imputing, so integer presence tables stay integer. This changes no result (scikit-learn casts
   to float32 internally) and halves memory on the 246k-row dataset.
4. **Spearman matrix** is not rounded to four decimals before clustering (the old code did);
   §3 S5 specifies `d = 1 − ρ` without rounding. NaN correlations become distance 1.
5. **Per-class heatmaps** use Spearman correlation (§3 S7); the old app used Pearson.
6. **Visualisations use all rows** (train + validation + test) of the preprocessed final
   features, as the old app used train + validation. Test rows are used for figures only, never
   for any decision.
7. **Sample dataset** (D8): 1,000 stratified rows × 500 reactions (100 top-importance + 400
   random), 4 significant digits, gzip, ~1 MB. See `fastforest/data/README.md`.
8. **Boruta** 0.4.3 installs and runs without warnings on numpy 2.5 / scikit-learn 1.9 (checked
   2026-10-12), so it is in the `bench` extra.
9. **Reported bound metrics.** The reference for the bound is the full model's *validation*
   metrics; the search never sees the test split. Test metrics for all three models are computed
   once, after every choice has been made.
10. **CLI `--split`** offers `stratified` and `random` only; `index` is available in the library
    and the app, where supplying the row list is practical.
11. **Train metrics.** The Phase 2 test list asks for metrics on train/val/test, while §3 lists
    validation and test. Train metrics are now recorded as well (`metrics[stage]["train"]`);
    only validation metrics ever drive a decision.
12. **`tests/test_reduce.py` assertion "all informative features retained at bound = 0.01".**
    On the prescribed `make_classification` dataset this is not a property of the method: its
    objective is the *smallest* subset within the bound, so with 10 informative and 10
    redundant (linear-combination) columns it keeps 8–14 signal columns and never a noise
    column (checked over 12 seeds and three `class_sep` settings; the same holds with
    `n_redundant=0`, where 4–10 of 10 informative columns are kept). The test therefore
    asserts what the method guarantees (every selected feature is signal, ≥ 80% of noise
    dropped, bound satisfied on validation) and the "all retained" intent is tested on a
    second dataset where each signal feature is necessary (class = arg-max of three
    Gaussian columns plus noise). Worth a sentence in the paper: FastForest selects a
    sufficient subset, not every informative feature.

## Interpretations made in Phase 3 (benchmark)

1. **L1-logistic C.** With the CV-best C the LASSO baseline kept 8,158 of 8,306 features on the
   body-site data, i.e. no selection. The benchmark therefore picks C by the one-standard-error
   rule on the 5-fold CV accuracy curve (the strongest regularisation within one SE of the best,
   as glmnet's `lambda.1se`), which is still "C by 5-fold CV on train" (§6.2). Both C values are
   recorded per run; `rule: cv` in the config restores the plain CV-best choice.
   **Solver (2026-10-12, speed-up):** multinomial saga needed > 10 min for one converged fit on a
   12k × 5.4k training split (21 min for the whole CV at 8 classes, > 60 min at 39 classes).
   liblinear one-versus-rest fits the same problem in ~50 s with fewer non-zero coefficients
   and equal validation accuracy (0.9997 vs 0.9975 for a loosely converged saga), so the
   baseline uses liblinear OvR with the fold × C grid run in parallel and C ∈ logspace(−3, 2, 6).
   The three L1 runs completed with saga were discarded and redone.
   **Grid cap (2026-10-13):** the first liblinear grid went up to C = 100; on the combined phylum
   table the C = 10 and C = 100 fits ran all night (six joblib workers, ~31 CPU-hours, no
   convergence; Tim's laptop ran hot). The grid is now C ∈ {1e-3, 1e-2, 0.1, 1} with
   `max_iter = 100` (convergence warnings are counted per run), and the per-run timeout is 3 h
   so a pathological run is recorded as a timeout instead of occupying the machine.
   Each worker now runs in its own process group and a timeout or a stop of the driver kills
   the whole group: killing only the worker would orphan its joblib children, which keep
   computing (regression test `test_timeout_kills_the_worker_and_its_children`). L1 on the
   three genus tables (64–105 classes, one binary fit per class) runs seed 0 only. Measured at
   low priority: 78 / 88 / 44 min (combined / 150k / 90k); four more seeds on the combined table
   would add ~5 h, so Tim decided on 2026-10-16 to report L1 at genus level as a single run. The campaign runs at `nice 19` so the laptop stays usable; wall-clock
   times of runs made while Tim worked are therefore noisy, and the scalability table (T3)
   must be timed on an otherwise idle machine.
   **Log flood (2026-10-16):** `fastforest_perm` on the combined phylum table, seed 2, printed
   one scikit-learn warning ("`sklearn.utils.parallel.delayed` should be used with
   `sklearn.utils.parallel.Parallel`…") 2,476,354 times in 5 min, 833 MB of the shared log.
   scikit-learn's parallel wrapper resets the warning filters on every call, which defeats
   "print once". The warning means scikit-learn's settings were not handed to a worker; they
   are the defaults here, so results are unaffected (that run: 97 features, test accuracy
   0.9922, 294 s; seeds 0/1/3: 54–136 features, 0.990–0.995, 283–318 s). From 2026-10-16: the warning is silenced in every worker (filter + `PYTHONWARNINGS` for joblib's
   processes), each run writes its output to `results/runs/<table>/<method>/seed<k>.log`, logs
   over 20 MB are gzipped, and the old shared log is archived as
   `results/campaign_2026-10-12_to_16.log.gz` with a filtered copy
   (`results/campaign_2026-10-12_to_16.filtered.log`) that drops the repeated warning.
2. **Boruta trees.** `BorutaPy(n_estimators="auto")` would grow ~1,000 trees per iteration on
   5,000 features; the plan says the S2 hyper-parameters, so 100 trees are used.
3. **Class filtering.** Rows without a label are dropped; classes with fewer than 10 rows are
   dropped before and again after the stratified 20,000-row subsample (seed 0, shared by all
   methods and seeds), so every class has at least 6/2/2 rows in train/val/test. Combined set:
   Phylum 14 → 11 classes in the comparison subset, Order 59 → 39.
4. **Peak memory** is the worker process's `ru_maxrss` (one process per dataset × method × seed),
   which includes loading the prepared table.
5. **Seed allocation.** Timing on the 20,000-row gut-MAG phylum table (seed 0, M2 Pro): FastForest
   MDI 20 s, no-selection/random < 15 s, RFECV 5.2 min, permutation threshold 5.5 min,
   FastForest permutation 6.4 min, L1 logistic 21 min, Boruta 15 min (54 min for all eight;
   the 39-class order tables are slower still). A first launch with 10 seeds projected ~36 h, so
   Tim asked for it to be faster (2026-10-12). Now: the bundled body-site table runs every method
   with 10 seeds; the six lab tables run every method with 5 seeds (§6.3 allows 5 where runtime
   demands it). Jobs run seed-major so that every dataset × method has a seed-0 result early.
   Runs completed under the 10-seed launch were kept (same protocol, same splits).
   **2026-10-15 (Tim):** seeds 1–4 on the combined table only; the 150k (sequenced genomes)
   and 90k (gut MAGs) tables, its two halves, keep seed 0 as a robustness check. The combined
   table is what the manuscript used (its references cite "150k and 90k data" together).
   Remaining time ~35 h → ~18 h at low priority; 244 runs in total. Stability (Jaccard across
   seeds) is therefore reported for body site and the three combined tables only.
7. **Shared permutation importances.** `fastforest_perm` (stages S2–S3) and the
   `perm_threshold` baseline fit the same S2 forest on the training split and compute the same
   seeded permutation importance on the validation split, so `fastforest_perm` writes its
   importances to `results/cache/<dataset>/perm_importance_seed<k>.csv` and `perm_threshold`
   reuses them (recorded as `from_cache`). Results are bit-identical; it saves ~5 min per
   dataset × seed. The baseline's *selection time* is then not measured separately: report it
   as the permutation-importance time from `fastforest_perm`'s `timings` (S2 + S3).
6. **FastForest with permutation importance** on the lab data often finds fewer than 100
   features with positive permutation importance, cannot meet the bound within that set, falls
   back to all of them and therefore selects exactly the permutation-threshold baseline's set
   (identical metrics on the gut-MAG phylum table). This is a real property of the method worth
   stating in the paper rather than a bug.
